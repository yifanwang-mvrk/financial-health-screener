# 1. 项目目标

## 1.1 商业问题

本项目研究的是：

> 能否利用公开可获得的财务信息，在一家上市电商相关企业陷入严重财务困境之前，识别其财务状况正在恶化的迹象？

本项目并不只是回答：

> 哪些公司目前的财务比率比较差？

相反，它试图回答三个彼此关联的分析问题。

### Q1. 财务健康评估

每家公司的当前财务状况有多健康？

### Q2. 早期预警验证

在历史上已经发生严重财务困境的案例中，哪些财务和经营指标曾提前恶化？

### Q3. 当前企业筛选

目前仍在上市的企业中，哪些公司正在同时出现过去已经被验证过的恶化信号？

---

## 1.2 目标用户

潜在用户包括：

- 信贷分析师
- 公司银行业务从业者
- 投资分析师
- 风险管理团队
- 战略团队
- 公司金融团队
- 商业智能用户

这些用户需要的不只是一个数值分数。

最终输出应当能够解释：

- 哪家公司需要重点关注
- 哪些风险信号被触发
- 这些信号是持续性的，还是暂时性的
- 公司与相关可比企业相比表现如何
- 哪些指标并不适用于该公司的商业模式
- 数据质量问题是否会影响最终结论

---

## 1.3 预期最终产品

本项目计划最终形成一个：

> **可解释的财务健康与早期预警筛选系统**

可能的输出包括：

- 公司风险排序表
- 财务健康指标
- 财务恶化标记
- 同行或同类企业基准
- 历史财务困境案例验证
- 公司层面的风险解释
- Power BI 仪表板
- 方法论与局限性报告

因此，本项目：

- 不只是一个仪表板
- 不只是一个 Python 模型
- 不只是一组财务比率

它是一套完整的 **决策支持工作流**。

# 2. 端到端项目逻辑

完整项目遵循以下流程：

```text
商业问题
    ↓
样本设计
    ↓
数据源发现
    ↓
原始数据收集
    ↓
数据质量验证
    ↓
数据标准化
    ↓
数据库构建
    ↓
SQL 指标计算
    ↓
财务恶化信号
    ↓
历史案例验证
    ↓
当前企业筛选
    ↓
Power BI 与商业沟通
```

每一个阶段都有不同的职责。

后面的阶段不应当静默地替前面的阶段修复问题。

例如：

- Power BI 不应静默修复错误的原始数据。
- SQL 不应隐藏不一致的会计定义。
- Python 验证程序不应自行做出缺乏依据的商业判断。
- 原始 CSV 文件中不应出现没有记录和说明的衍生数据。

# 3. 项目阶段

## 3.1 阶段 A1 — 样本设计

### 核心问题

哪些公司应该被纳入研究？哪些公司之间具有合理的可比性？

### 主要活动

- 建立候选公司全集
- 记录公司身份与上市状态
- 分类商业模式
- 分配初步同行组或可比组
- 判断公司是否为核心样本候选
- 记录纳入原因与排除原因
- 识别边界案例
- 识别历史财务困境参考案例

### 主要文件

```text
data/raw/sample_companies_master.csv
docs/a1_sample_design/
src/check_sample_master.py
```

### 重要原则

```text
include_in_core_sample = 1
```

只代表一项初步的研究设计决策。

它并不能证明：

- 公司的历史财务数据覆盖足够完整
- SEC 数据一定可获得
- 不同公司的会计概念具有可比性
- 该公司一定会保留在最终分析样本中

在完成数据源发现、会计处理审查和数据质量验证之后，最终样本仍可能发生变化。

## 3.3 阶段 A3 — 数据标准化

### 核心问题

如何将不同公司、不同申报文件、不同货币、不同单位以及不同会计概念，转换为统一且可比较的数据语言？

### 主要活动

- 标准化单位
- 标准化货币
- 标准化日期和财政期间处理
- 标准化正负号规则
- 将原始来源概念映射为项目统一字段
- 区分报告值与衍生值
- 正确保留缺失值
- 创建数据质量标记
- 创建指标适用性标记

### 标准化规则示例

- 货币金额统一存储为 **百万美元**
- 流通股数量统一存储为 **百万股**
- 资本支出存储为 **正数形式的现金流出金额**
- 未报告存货时，不得用零替代
- Amazon 的毛利润应标记为衍生值
- eBay 的终止经营问题应保留在备注或标记字段中

### 主要输出位置

```text
data/normalized/
```

标准化数据应当回答：

> 不同数据源和不同公司申报文件，如何使用同一种项目数据语言？

## 3.5 阶段 A5 — 财务指标工程

### 核心问题

哪些财务指标能够描述公司的盈利能力、流动性、杠杆水平、现金流质量、增长以及经营恶化？

### 可能的指标

#### 盈利能力

- 毛利率
- 营业利润率
- 净利润率
- 总资产收益率
- 净资产收益率

#### 流动性

- 流动比率
- 现金比率
- 营运资本

#### 杠杆水平

- 总负债与总资产比率
- 长期债务与总资产比率
- 债务权益比

#### 现金流

- 经营现金流利润率
- 自由现金流利润率
- 现金转化相关指标

#### 增长与恶化

- 营业收入增长率
- 利润率变化
- 多年度营业收入下降
- 多年度利润率恶化
- 现金流由正转负

### 重要原则

一个指标在数学上可以计算，并不意味着它在经济意义上一定有价值。

例如：

- 当净资产为负时，ROE 可能具有误导性。
- 对轻资产型平台而言，存货周转率可能不适用。
- 一次性资产处置可能扭曲净利润。
- 不同收入确认模式可能影响利润率之间的比较。
- 一个很大的比率可能只是因为分母过小，而不是真正的经营改善。

因此，指标计算应当同时配备：

- 适用性标记
- 数据质量标记
- 会计处理说明
- 必要时的人工复核警告

## 3.6 阶段 A6 — 早期预警信号设计与验证

### 核心问题

在严重财务困境发生之前，哪些指标或指标组合曾经提前出现？

### 候选信号

候选信号可能包括：

- 营业收入连续多个期间下降
- 营业利润率持续恶化
- 经营现金流由正转负
- 自由现金流持续为负
- 杠杆水平显著上升
- 流动性持续减弱
- 存货增长速度远高于营业收入
- 多个指标同时恶化

### 验证问题

在一个信号被正式接受之前，项目应当回答：

- 该信号是否在财务困境事件发生前出现？
- 它提前了多长时间出现？
- 该信号是否也经常出现在健康公司中？
- 它是否适用于所有商业模式？
- 多个信号的组合是否优于单个孤立指标？
- 结果是否由一次性会计事件导致？
- 结果是否对阈值的选择非常敏感？
- 该信号是否具有经济意义，而不仅仅是统计上异常？

> 一个信号必须经过验证，才能被称为早期预警指标。

- 历史指标趋势
- 数据质量警告
- 公司详情页面
- 方法论页面
- 局限性页面

### 主要位置

```text

```

### Power BI 的角色

Power BI 是项目的 **展示层和决策支持层**。

它不应成为唯一保存重要逻辑的地方。

关键的数据清洗、会计处理、指标计算和风险逻辑，通常应当在数据进入 Power BI 之前完成并记录。

# 5. 文件夹职责

## 5.1 `data/raw/`

### 用途

保存原始数据或接近原始状态的项目输入。

### 当前示例

```text
sample_companies_master.csv
financial_statements_template.csv
financial_statements_raw.csv
```

### 规则

原始数据不应被静默覆盖。

当一个原始值需要更正时：

1. 核实原始数据来源。
2. 记录为什么需要修改。
3. 保留相关备注或来源信息。
4. 重新运行验证。
5. 使用清晰的提交信息记录该变化。

---

## 5.2 `data/interim/`

### 用途

保存数据处理过程中产生的临时中间数据。

### 可能示例

- 部分清洗后的 SEC 提取结果
- 临时会计概念映射表
- 等待人工审查的数据
- 最终标准化前的合并数据
- 临时提取输出

中间数据不能被默认视为已经可以直接分析。

它们可能仍然包含：

- 不一致的单位
- 尚未解决的数据源概念
- 缺失的分类
- 重复观测
- 需要人工检查的数值

---

## 5.3 `data/normalized/`

### 用途

保存已经应用统一项目定义的数据。

### 标准化可能包括

- 统一货币
- 统一日期格式
- 统一正负号规则
- 统一会计概念
- 明确的缺失值标记
- 明确的适用性标记
- 报告值与衍生值分类

标准化数据回答：

> 不同数据源如何使用同一种项目数据语言？

## 5.6 `src/`

### 用途

保存用于可重复项目工作流的正式 Python 源代码。

# 8. 数据质量的五个层级

## 第 1 层 — 文件与结构

### 核心问题

- 文件是否存在？
- 所有必需列是否存在？
- 列顺序是否正确？
- 是否存在意外的额外列？

### 示例

```text
缺少 revenue 列。
```

---

## 第 2 层 — 格式与类型

### 核心问题

- 财政年度能否转换为数字？
- 期间结束日期能否被解析？
- 财务数值能否转换为数字？
- 二元字段是否使用允许的格式？

### 示例

```text
revenue = "five million"
```

---

## 第 3 层 — 唯一性与跨表完整性

### 核心问题

- 公司—年度键是否唯一？
- 每一个财务数据中的股票代码是否都存在于公司主表？
- 表之间的关系是否有效？

### 示例

```text
AMZN + 2023 出现了两次。
```

---

## 第 4 层 — 会计规则与商业规则

### 核心问题

- 总资产是否等于总负债加所有者权益？
- 按照项目定义，自由现金流是否等于经营现金流减资本支出？
- 资本支出是否使用要求的符号规则？
- 条件性样本设计规则是否满足？
- 报告值与衍生值是否正确分类？

### 示例

```text
total_assets != total_liabilities + total_equity
```

```text
free_cash_flow != operating_cash_flow - capital_expenditure
```

这些检查目前尚未完整实现。

---

## 第 5 层 — 分析合理性

### 核心问题

- 极高的增长率是真实变化，还是单位错误？
- 异常高的利润率是否由一次性收益导致？
- 该比率是否适用于该商业模式？
- 分母是否接近零？
- 该观测是否需要人工检查？
- 公司特有的会计事件是否扭曲了趋势？

### 示例

```text
营业收入同比增长 950%。
```

该数值可能是真实的。

因此，它通常应当产生警告或人工复核标记，而不是被程序自动修正。

# 11. 虚拟环境与依赖

## 11.1 `.venv`

`.venv` 是项目专属的 Python 环境。

当终端提示符显示：

```text
(.venv)
```

说明虚拟环境已经激活。

---

## 11.2 在 macOS 上激活环境

```bash
source .venv/bin/activate
```

该命令不会重新安装软件包。

它的作用是告诉当前 Shell：

> 优先使用 `.venv` 中的 Python 解释器和软件包。

---

## 11.3 确认当前 Python 解释器

```bash
which python
```

返回的路径应当指向项目中的 `.venv`。

示例：

```text
.../financial-health-screener/.venv/bin/python
```

查看 Python 版本：

```bash
python --version
```

---

## 11.4 安装软件包

```bash
pip install pandas
```

该命令会将 `pandas` 安装到当前激活的 Python 环境中。

每次打开 VS Code 时，通常不需要重新安装软件包。

软件包会一直保留，除非：

- 环境被删除
- 环境被替换
- 环境损坏
- 软件包被主动卸载

---

## 11.5 重建项目环境

一个典型的环境搭建流程是：

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

这样，其他用户无需获得原始 `.venv` 文件夹，也能够重新构建项目环境。

- 为什么需要执行
- 预期输出是什么
- 如果失败，可能意味着什么

## 13.4 按输入、处理和输出解释代码

对于重要代码，应当解释：

### 输入

### 处理

程序执行什么验证、转换或计算？

### 输出

程序会生成什么结果、文件、表、警告或错误？

### 与项目的关系

- 为什么需要这段代码？
- 哪些地方可能失败？
- 哪个项目阶段使用它的输出？
- 后续哪个步骤依赖它？

- 每个文件为什么存在

# 14. 故障排查地图

当出现问题时，首先判断问题属于哪个层级。

## 14.1 Shell 层问题

### 示例

```text
command not found
```

### 可能原因

- 命令拼写错误
- 程序尚未安装
- 环境路径错误
- 命令被输入到了错误的界面

---

## 14.2 Python 环境问题

### 示例

```text
ModuleNotFoundError: No module named 'pandas'
```

### 可能原因

- `.venv` 尚未激活
- VS Code 与 Terminal 使用不同的 Python 解释器
- `pandas` 安装在另一个环境中
- 软件包尚未安装

---

## 14.3 文件路径问题

### 示例

```text
FileNotFoundError
```

### 可能原因

- Terminal 不在项目根目录
- 文件名错误
- 相对路径错误
- 文件被移动
- 文件尚未保存
- 脚本预期的文件夹结构不同

---

## 14.4 数据结构问题

### 示例

```text
Column structure does not match expected schema.
```

### 可能原因

- 缺少必需列
- 存在意外的额外列
- 列名拼写错误
- 列顺序错误
- 加载了错误的文件

---

## 14.5 数据规则问题

### 示例

```text
Duplicate ticker-fiscal_year rows found.
```

### 含义

程序本身可能运行正常。

真正的问题是输入数据违反了项目规则。

这与 Python 程序错误或 Shell 错误不同。

---

## 14.6 Git 界面问题

### 示例

文件显示：

```text
U
```

### 含义

- 文件已经存在
- 文件是新文件
- Git 尚未跟踪该文件

这不代表文件尚未保存。

---

## 14.7 Pager 问题

当 `git diff` 打开全屏页面时：

```text
按 q 退出。
```

在正常终端提示符重新出现之前，不要输入 Shell 命令。

在 Pager 中输入的命令，会被 Pager 解释，而不是被 Shell 执行。

# 18. 最终项目心智模型

项目应当始终通过以下链条来理解：

```text
商业问题
    ↓
公司样本
    ↓
可靠的数据来源
    ↓
原始数据
    ↓
验证
    ↓
标准化
    ↓
数据库与 SQL
    ↓
财务指标
    ↓
经过验证的风险信号
    ↓
可解释的企业筛选
    ↓
Power BI 与决策支持
```

Python、SQL、Git、VS Code、DuckDB 和 Power BI 的目的，并不是替代商业判断。

它们的作用是让商业分析变得：

- 可靠
- 可重复
- 可追溯
- 可扩展
- 可解释

# 19. 项目核心原则

> Financial Health Screener 的价值，并不来自计算尽可能多的财务比率。

它的真正价值来自建立一条透明的逻辑链：

```text
可靠的财务数据
    ↓
具有经济意义的指标
    ↓
经过历史验证的恶化信号
    ↓
可解释的商业决策
```

每一个新文件、脚本、数据表、指标和仪表板元素，都应当加强这条逻辑链。
